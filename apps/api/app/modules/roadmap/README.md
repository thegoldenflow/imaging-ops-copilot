# Roadmap cards and safety tiers (spec 8.1, 8.3, WP10)

The architecture pages: **Roadmap** (`/roadmap`, one card per module the platform could grow, none implemented) and
**Safety tiers** (`/safety`, the three risk tiers, the tool side-effect levels, the Level 0–4 mapping, guardrails,
honest boundaries, the 6.7 positioning sentences). Any signed-in user. Web: `apps/web/src/features/roadmap/`. API:
`GET /api/roadmap`, `GET /api/roadmap/safety` (`router.py`). Doc: [docs/safety-tiers.md](../../../../../docs/safety-tiers.md),
generated by `scripts/safety_doc.py` from the same views.

This README also covers the three 8.1 stubs that run once in the hospital storyline on preset data: registry modules
`critical_value_routing` (step 4, INR 3.8 against a preset threshold 3.5), `deterioration_alert` (step 8, a preset
NEWS2 of 7) and `coding_assist` (step 12, preset ICD-10-CA and CCI codes). Their cards are written by
`app/modules/storyline/stubs.py`; they contain no clinical logic.

## Input resources

- `config/roadmap.yaml`: one card per row of the spec's 8.1 table (pain, data source, risk tier, what it reuses and
  the files it would reuse, how the demo handles it, the registry entry and storyline step where there is one) and
  the fixed footer.
- `config/safety.yaml`: the words only (tier definitions, allowed AI actions, regulatory notes, side-effect levels'
  preconditions, the Level 0–4 mapping, guardrails with their code paths and evidence, honest boundaries,
  positioning sentences).
- The agent and tool registries (`config/agents/`, `config/tools/`), the storyline's steps
  (`app/modules/storyline/script.py`) and the eval runs (`evals/runs/`), read when a view is built.
- The stubs: the storyline preset's Observation (INR), the preset NEWS2 score in the flowsheet, the signed discharge
  summary; thresholds and codes in `app/modules/storyline/script.py`.

## Output schema

- `GET /api/roadmap`: `{footer, cards[{id, title, pain, data_source, risk_tier, reuses, reuse_refs[], demo,
  demo_note, registry, storyline, spec_ref, registry_entry, step{n, key, title, stub, href}, footer}], counts}`
  (`service.cards_view`).
- `GET /api/roadmap/safety`: `{tiers[{..., entries[], signoff_roles[], counts, reach{level: [agent ids]}}],
  side_effect_levels[{..., tools[]}], level_mapping[], guardrails[{..., live}], honest_boundaries[{id, text, facts}],
  positioning[], definition_of_done, platform}` (`service.safety_view`).
- The stubs' output: an `ai-review` Task through `submitForReview` (critical value, NEWS2 nurse card, coding
  suggestion) and a `news2` Flag through `createFlag`, each saying it is a roadmap item.

## Eval set and threshold

Nothing here is a model. The stubs' registry entries have eval status `not_applicable` (preset data). The pages are
checked by `tests/test_roadmap.py`: one card per row of the spec's 8.1 table in order with the same tiers, the cards'
registry entries and tiers agree with the registry, the storyline stubs link to their step, every registry entry is
in exactly one tier and every tool in one level, the guardrails read the latest runs, the API answers every role, and
`docs/safety-tiers.md` is current (`service.check()` lists any drift). Playwright: `e2e/roadmap.spec.ts`.

## Known failure modes

- The cards are words: nothing in them is implemented, and the reuse references point at the code a module would
  build on, not at a working feature.
- The stubs only work on the storyline's preset patient: the critical-value threshold, the NEWS2 score and the codes
  are preset, not computed, and no other patient gets a stub card.
- The safety page reads every run file that holds a platform suite when the runs change (cached afterwards); with
  hundreds of runs the first request would slow down.
- `docs/safety-tiers.md` must be regenerated after a registry change (`uv run python scripts/safety_doc.py`); the
  backend suite fails until it is.
