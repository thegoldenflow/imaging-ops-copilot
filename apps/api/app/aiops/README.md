# AI Ops: registries, Eval Center, release gate, observability, alerts (spec 6.6)

One command runs every agent's eval set and writes a run file; the release gate derives each agent's eval status
from its latest run; one page shows pass rates, override rates, latency, cost and failures from the traces, with a
drill-down to the trace in two or three clicks. Web: **AI Ops** (`apps/web/src/features/ai-ops/`; admin, operations
manager, medical director; the radiologist sees the Eval Center, Compare, Registries and Imaging reports tabs). API:
`/api/aiops/...` (`router.py`). Registry module `ai_ops` (no model) writes the alert Tasks.

| File | What it does |
| --- | --- |
| `evalrun.py` | The one runner: `uv run python -m app.aiops.evalrun [AGENT ...] [--live] [--prompt agent@n] [--model entry] [--stamp] [--check] [--no-platform]` (`make eval AGENT=...` with GNU make) |
| `suites.py`, `collect.py` | Suites that wrap the modules' own harnesses (imaging functions, de-identification, triage regression, Control Tower, medication safety, documentation, front desk; module reports through the registry); per-case cost and latency |
| `runs.py`, `release.py` | Run files in `evals/runs/`; the release gate (eval status from the newest run of the prompt version in use) |
| `promptgate.py` | The prompt gate: each prompt file's `eval_run` header names a run that evaluated exactly its text and met the bar |
| `observe.py`, `cost.py` | Aggregates from traces, Tasks and workflow runs by agent, model, unit and day; list-price estimates for mock calls |
| `alerts.py` | Daily cost and failure-rate alerts from `config/alerts.yaml`, one admin Task per alert, scope and day |

## Input resources

- Registries: `config/agents/*.yaml` (`eval_threshold`, `prompt_version`, `model_policy`), `config/models.yaml`
  (provider, tier, the setting that holds the model id, approved tasks, allowed risk tiers, `max_cost_per_case`,
  data handling), `apps/api/prompts/<agent>/<n>.md` (four-line header: author, change_note, approved_by, eval_run),
  `config/alerts.yaml`.
- Eval sets: `evals/<agent or module>/cases.jsonl` and `evals/datasets/*.json` (imaging), through the suites; the
  common case view `{id, agent_id, source, input_refs, expected}`.
- Production data: `agent_traces` (runs, LLM calls, tool calls, human actions, cost), FHIR Tasks (adoption,
  escalation, completion) and `workflow_runs` (cost per completed workflow), read for a time window.

## Output schema

- Run file `evals/runs/run-<YYYY-MM-DDTHHMMSS>.json`: run id, times, mode, variant, git commit, and per agent the
  suite, source, agent and prompt version, prompt hash, model, threshold, the six common metrics (`schema_validity`,
  `grounding_rate`, `task_success`, `human_override_rate`, `latency_p50_ms` / `latency_p95_ms`,
  `cost_per_case_usd`), the module's extra metrics and gates, the verdict, per-case results and the traces of failing
  cases; for a suite that also calls agents that are not its own, the whole case (`pipeline`); platform suites
  (injection, workflows, simulator). Field list: `docs/data-model.md`, "AI Ops (WP10b)".
- Effective eval status (`release.derive`): `status` passed / pending / failed, `run_id`, `task_success`,
  `threshold`, `mode`, `note` — what the runtime watermarks (**Not evaluated**, **Eval failed**) or refuses in prod.
- Overview (`observe.overview`): the six cards, the agent table, dimension tables and the failure list.
- Alert Task: FHIR Task code `ai-ops-alert`, performer admin, no patient.

## Eval set and threshold

AI Ops has no model of its own: it is the place where every agent's eval and threshold are applied. Its own checks are
`tests/test_aiops.py` (runner, release gate, observability, alerts, the page's no-hard-coded-numbers grep) and
`tests/test_prompt_gate.py` (every prompt version evaluated with the same text and, in use, at or above its bar). The
summary of every agent's latest result is [evals/README.md](../../../../evals/README.md), generated by
`scripts/eval_summary.py`; run files are described in [evals/runs/README.md](../../../../evals/runs/README.md).

## Known failure modes

- Every committed run is a mock baseline (no live run yet), so the release gate keeps the agents `pending` and their
  output carries **Not evaluated**; a mock run never passes an agent except a pipeline eval (de-identification).
- The human ratings (Control Tower narratives, documentation) stay outside the runner; their sheets are unscored.
- A report-only suite (a module's own report: `call_center`, `followup_calls`) has no per-case cost or latency.
- The whole-case cost of a suite that also runs other agents (`pipeline`) is reported, not gated: the
  `cost_per_case` gate compares an agent's own calls with its own model's max.
- `followup_calls`: the newest run that names it (`run-2026-10-10T063931`) found no eval set, so its release status
  says "not evaluated in the latest run" although an earlier run judged its module gates; a new run of the agent fixes
  it (see evals/README.md).
- The failure list and the dimensions read the window's traces on each request (an indexed time query): fine at demo
  volume, a pre-aggregated table at hospital scale.
- Alert Tasks have no screen besides AI Ops (admins cannot read Tasks through FhirGateway under the 6.3 RBAC; the
  `ai_ops` module reads and closes them on their behalf, audited).
- Two agents have no eval set: `cxr_draft` (needs images) and `prep_translation`.
