# 影像中心 AI 工具套件 · 系统清单（Claude Code 开发用）

Oct 6, 2026 · @Ping

## 项目目标与范围

用合成数据做一套可演示的影像中心 AI 工具，覆盖 [GNMI 招聘描述](https://ca.indeed.com/viewjob?jk=406e8f4b0487c06e)里的 21 个系统，分 5 个阶段交付。它是申请 AI Developer 岗位时的作品链接，也用于面试现场演示。

产品用中性名字（暂定 Imaging Ops Copilot），不使用 GNMI 的名称、标识或真实诊所地址。建议投递前完成阶段 0 和阶段 1，其余阶段边投边做，作品链接持续更新。

> **第一批开发范围：系统 1–4（Backend Infrastructure、Scheduling Command Center、Report Generator、Front Desk Automation）。这四项对应 JD 的 Priority Projects；其余系统作为后续扩展。**

硬性约束：

- 只用合成数据：患者、医生、申请单、预约全部由 seed 脚本生成，仓库里不出现任何真实 PHI。
- AI 只给建议：所有 AI 产出都是建议或草稿，必须有人确认才生效，界面上明确标注哪些内容由 AI 生成。
- 可降级：Claude API 不可用时，各系统的非 AI 功能照常运行。
- 外部系统全部模拟：RIS、PACS、OHIP 健康卡验证、电话、短信、邮件、外院影像库都用本地 mock 服务。
- 语言：界面、代码、注释、提交信息用英文；面向患者的内容支持多语言。

不做的事：

- 不接真实 RIS、PACS 或 OHIP，不处理真实患者数据。
- 不追求诊断准确性：胸片报告只演示工作流和评测方法，不作为医疗器械。
- 不做原生 App：患者端用响应式网页。

## 端到端演示主线

演示时用一位合成病人走完三段流程，串起 12 个系统。Seed 数据要专门造出这位病人（首选语言为中文）和整条故事线，并能一键重置。

&#91;embedded content: 演示主线 · 3 段、13 步、12 个系统\]

第一段，胸片初稿提示可疑结节，医生审改签发后通知家庭医生。第二段，家庭医生在门户加开增强 CT，申请单依次完成分诊、方案推荐和造影剂核查。第三段，另一位患者打电话取消，空出的时段自动补给这位病人，随后发出中文须知、调取外院旧片，检查完成后记录剂量。

## 技术栈与仓库结构

前端 React + TypeScript，后端 Python FastAPI，PostgreSQL 存数据，Temporal 跑持久化工作流，Orthanc 模拟 PACS，全部用 Docker Compose 一键启动。

&#91;embedded content: 系统架构 · 5 个服务组件、3 个外部依赖\]

所有 AI 请求，包括语音管线里的 Claude 调用，都先经过调用层去标识化和记日志，再发往 Anthropic API。

- 前端：React、TypeScript、Vite、Tailwind、shadcn/ui；图表用 Recharts，数据请求用 TanStack Query；API 类型由 FastAPI 的 OpenAPI 定义自动生成（openapi-typescript）。
- 后端：Python 3.12、FastAPI、SQLAlchemy、Alembic 迁移、Pydantic 校验；爽约预测用 scikit-learn。
- AI：Anthropic Python SDK，模型 ID 放环境变量。
- 工作流：Temporal Python SDK。
- 影像：Orthanc（Docker）加 pydicom；看片先用普通图片查看器，需要时换 Cornerstone3D。
- 语音：浏览器经 WebSocket 推流；STT 和 TTS 做成可插拔接口；可选 Twilio。
- 测试：pytest、Vitest、Playwright。

## 【第一批】阶段 0：后端基础设施（系统 1）

先搭所有系统共用的底座：认证权限、PHI 保护、审计、Claude 调用层、模拟外部服务和合成数据。阶段 0 没通过验收，后面的系统都不开工。

- 认证与角色：角色包括前台、技师、放射科医生、运营经理、医疗总监、管理员、转诊医生；每个接口按角色和站点校验权限。演示模式在登录页一键切换角色。
- PHI 保护：PHI 字段在应用层加密，密钥放环境变量；日志和错误追踪里不出现 PHI 原文。
- 审计日志：中间件自动记录每次 PHI 读写，包括用户、角色、时间、记录、动作、来源 IP、访问原因。日志只追加不修改，用哈希链防篡改。
- Claude 调用层：所有 AI 功能只能通过它调用 Claude，规范见“Claude 调用规范与 AI 评测”一节。
- 集成适配层：RIS 接口按 FHIR 资源风格设计；PACS 用 Orthanc，预置样例 DICOM；外院影像库、OHIP 验卡、短信、邮件、电话都是本地 mock，可配置延迟和失败率。
- 工作流：Temporal 运行所有定时和长流程任务（提醒、补位邀约、危急结果升级、旧片调取），服务重启不丢任务。
- 合成数据：一条命令生成默认规模的数据，即 5 个站点、12 台设备、2000 名患者、150 名转诊医生和 3 个月预约历史（含取消和爽约），外加演示主线的那位病人；可一键重置。
- 监控：健康检查接口、结构化日志，以及每个 AI 功能的调用量、延迟、失败率和成本看板。

验收：

- [ ] `docker compose up` 加一条造数命令后，前端能登录并切换角色
- [ ] 越权访问一律返回 403，并留下审计记录
- [ ] 直接查数据库时，PHI 字段是密文
- [ ] Claude 调用层有单元测试，覆盖去标识化、schema 校验失败重试、超时降级

## 【第一批】阶段 1：旗舰系统

这 3 个系统对应 JD 里写得最详细的优先项目，也是投递时最该先放出来的演示。

### 【第一批】系统 2 · 排程指挥中心 Scheduling Command Center

用户是运营经理和排程员。

- 实时利用率看板：按站点和设备显示今天和本周的已约时长、空闲时长、利用率，外加站点 × 小时热力图。
- 取消自动补位：预约一取消，就从候补名单筛出站点可接受、检查类型匹配、来得及做准备的病人，排序后一键发邀约，先确认者得。
- 跨站点分流：标出排满和空闲的站点，建议把候补病人转到附近有空档的站点。
- 爽约预测：用历史数据训练 scikit-learn 模型，特征包括提前预约天数、过往爽约次数、星期与时段、是否确认提醒。每个预约显示风险分和前三个原因，高风险自动多发一次提醒。
- 优先排序：临床紧急度永远排第一。同一紧急度内，再按等待时长、检查价值、重要转诊医生加权；权重可配置，每个排序都能展开看得分构成。

验收：

- [ ] 取消一个预约后 5 秒内出现排好序的补位候选
- [ ] 看板随预约变化实时刷新
- [ ] 爽约模型在留出集上报告 AUC，界面显示每个预约的前三个风险因素

### 【第一批】系统 3 · 胸片报告生成 Report Generator

用户是放射科医生。

- 输入：上传胸片（PNG、JPEG 或 DICOM），或从 Orthanc 选一个检查；DICOM 先去掉患者标识字段再处理。
- 生成：Claude 视觉模型按固定 schema 输出初步结论，包括图像质量、分区所见（肺、胸膜、心脏纵隔、骨骼、管线）、印象、需紧急通知的发现、不确定之处。
- 审签：左边看片、右边草稿，医生逐段接受、修改或删除；签发后才算正式报告，签发前其他角色看不到草稿。
- 标注：草稿处处标明“AI 生成的初稿，仅供放射科医生审阅，不是诊断”；记录模型、prompt 版本和医生的改动量。
- 联动：医生确认的紧急发现自动建档到危急结果追踪（系统 12）。
- 样例图：取自公开的去标识化胸片数据集（如 NIH ChestX-ray14、Indiana University 的 Open-i），下载前确认各自的许可条款。

验收：

- [ ] 从上传到出草稿全流程可演示，输出符合 schema
- [ ] 后端强制：未签发的报告无法发给转诊医生
- [ ] 评测页显示草稿与数据集标签的一致率，并写明局限

### 【第一批】系统 4 · 前台自动化 Front Desk Automation

用户是患者和前台。

- AI 语音前台：浏览器内实时通话，链路是 WebSocket 流式 STT、Claude 工具调用、流式 TTS；可选接 Twilio 电话号码。能查预约、改约、取消、讲检查须知、讲地址和营业时间。
- Agent 工具：`lookup_appointment`、`reschedule`、`cancel`、`get_prep_instructions`、`get_site_info`、`transfer_to_human`。
- 安全规则：先核对姓名和出生日期，才谈预约细节；不回答医疗问题，一律转人工；每通电话保存转写、摘要和处理结果。
- 联动：语音取消会触发系统 2 的自动补位。
- 网上预登记：预约确认后发链接，患者填写资料、保险信息、同意书和首选语言。
- 自动提醒：预约后在检查前 72 小时和 24 小时发提醒（mock 短信和邮件），回复即可确认或取消。
- 保险核验：OHIP 健康卡验证和私人保险核验都用 mock 服务。

验收：

- [ ] 一通语音通话能完整走完核对身份、改约、确认
- [ ] 本地环境下，用户说完到 Agent 开口不超过 1.5 秒
- [ ] 新预约自动排好提醒；回复取消后时段释放并触发补位

## 阶段 2：申请单接收流水线

这 6 个系统是同一条流水线上的环节：申请单进来，Claude 只抽取一次结构化字段，后面各环节都读这份结果。执行顺序如下：

1. 申请单抽取（共用的第一步）
2. 分诊排序（系统 5）
3. 扫描方案推荐（系统 6）
4. 造影剂与肾功能检查（系统 7，只针对增强检查）
5. MRI 安全筛查（系统 8，只针对 MRI）
6. 预约之后，检查前须知（系统 9）和调取既往影像（系统 10）并行

### 共用第一步 · 申请单抽取

- 输入：申请单 PDF、扫描件或在线表单文本。
- 输出字段：申请的检查、临床指征、相关病史、提到的既往影像、过敏、肾病或糖尿病、植入物线索、医生标注的紧急程度。
- 每个字段附原文出处；低置信度字段标黄，等人确认。

* [ ] 抽取结果与原文出处并排显示，可人工改正

### 系统 5 · 分诊排序 Priority Triage

- Claude 根据抽取结果给出优先级分档（如 P1–P4）、理由和红旗症状；各档的目标等待天数做成配置。
- 队列按“距离目标期限还剩几天”排序，快超时的标红。
- 放射科医生可以改档，必须填原因；改档记录同时用作评测数据。

* [ ] 新申请单 1 分钟内完成分级并入队
* [ ] 改档有原因、有审计记录，评测脚本能算出模型与医生的一致率

### 系统 6 · 扫描方案推荐 Protocol Assignment Assistant

- 维护一个合成的方案库（例如“头颅 MRI 平扫加增强，癫痫方案”），每个方案写明适用指征、是否用造影剂、扫描时长。
- Claude 检索方案库，给出首选方案、两个备选、理由和是否需要造影剂；医生一键批准或改选。
- 批准的方案写回预约，扫描时长决定排程时段长度。

* [ ] 每张新申请单都有方案建议
* [ ] 采纳率和常见改选有统计看板

### 系统 7 · 造影剂与肾功能检查 Contrast & Renal Checker

- 只针对增强检查：是否有近期 eGFR，是否有造影剂过敏或既往反应，是否需要预防用药。
- 规则阈值（eGFR 多少需要处理、结果多久内有效）由医疗总监在配置页设定。Demo 里用占位值，不写死在代码里。
- Claude 只负责从申请单和问卷里抽出相关病史，判断交给规则，结果写明依据。
- 状态分为通过、需补 eGFR、需人工审核、需预防用药；检查日前仍未解决的自动提醒。

* [ ] 每个增强检查预约都有状态和依据
* [ ] 修改阈值后所有状态即时重算

### 系统 8 · MRI 安全筛查 MRI Safety Screening Assistant

- 预约后给患者发多语言在线问卷：心脏起搏器或除颤器、动脉瘤夹、人工耳蜗、神经刺激器、体内金属碎片、药物泵、近期手术、怀孕、幽闭恐惧等。
- 患者用自己的话描述的植入物，由 Claude 抽取成器械名称和类别，再对照内部器械清单（demo 用合成清单）。
- 系统只给“需审核”标记和理由，永远不能自动放行；技师或放射科医生审核后，预约才能确认。

* [ ] 问卷支持至少 4 种语言（如英文、法文、中文、旁遮普语）
* [ ] 有标记的预约在审核前无法进入“已确认”

### 系统 9 · 检查前须知 Patient Prep Instructions

- 按检查类型维护英文须知模板（禁食、用药咨询、着装、到达时间等），由临床人员审批。
- 译文不在发送时实时生成：先用 Claude 生成各语言草稿，人工审批后入库，发送时只取已审批的版本。
- 预约时和检查前 48 小时自动发送，语言跟随患者的首选语言。

* [ ] 每个新预约都按首选语言发出须知
* [ ] 未审批的译文无法发送

### 系统 10 · 调取既往影像 Prior Imaging Retrieval

- 从申请单抽取结果和患者历史里找出外院的既往检查，自动生成调取请求。
- Temporal 工作流向 mock 外院影像库发请求、等待、重试、超时；状态有已请求、已收到、未找到。
- 收到的影像导入 Orthanc 并关联到本次检查，放射科医生读片时可以直接对比。

* [ ] 预约后自动创建调取任务，看板显示状态
* [ ] mock 服务故意失败时，工作流按策略重试并给出最终结果

## 阶段 3：放射科运营

这 4 个系统让读片进度、紧急通知、报告质量和辐射剂量都有据可查。AI 用得少，重点在数据、流程和留痕。

### 系统 11 · 报告积压与周转追踪 Reporting Backlog & Turnaround Tracker

- 实时显示已扫描、未出报告的检查，按站点、检查类型、优先级、积压时长分组。
- 周转时间 = 终稿签发时间 − 检查完成时间；按优先级设目标，超时报警。
- 显示每位放射科医生的待读量，建议把积压改派给有空且有相应资质的医生。

* [ ] 看板随新检查和签发实时更新
* [ ] 改派操作写入审计记录

### 系统 12 · 危急结果追踪 Critical Results Tracker

- 医生在报告里标记需通知的发现后，自动建档：发现内容、紧急程度、开单医生、通知截止时间。
- Temporal 工作流：通知开单医生（mock 电话或传真），等待确认，超时按配置升级（如通知医疗总监）。
- 确认必须记录谁、何时、用什么方式；没有确认记录的案例不能关闭。

* [ ] 演示时故意不确认，能看到自动升级
* [ ] 每个案例都有完整时间线

### 系统 13 · 同行评审与质控 Peer Review / QA Module

- 按配置比例随机抽取已签发的报告，盲派给另一位放射科医生复核。
- 复核按分级打分（如一致、轻微差异、有临床意义的差异），并记录差异类型。
- 按医生和检查类型出质控报表，只有质控负责人能看。

* [ ] 抽样任务按计划运行，永远不会派回原报告医生
* [ ] 质控报表可导出

### 系统 14 · CT 剂量监测 CT Dose Monitoring

- 每次 CT 检查记录 CTDIvol 和 DLP 两项剂量指标；demo 用合成数值，数据结构参照 DICOM 剂量结构化报告。
- 按扫描方案配置参考水平，超出的检查进入异常列表，并可按设备和方案看趋势。

* [ ] 每次 CT 检查都有剂量记录
* [ ] 超出参考水平的检查出现在异常列表

## 阶段 4：业务与合规

最后 7 个系统大多是看板、对账和文档管理，单个复杂度低，适合在前面跑通后批量做。

### 系统 15 · 库存管理 Inventory Manager

- 按站点管理造影剂和耗材：批号、效期、库存量、补货点。
- 增强检查完成时自动扣减造影剂；低于补货点时生成补货提醒和采购单草稿；临期也提醒。

* [ ] 完成一个增强检查后，库存自动减少
* [ ] 低库存和临期都有提醒

### 系统 16 · 转诊分析看板 Referral Analytics Dashboard

- 按转诊医生、专科、检查类型、站点、时间看转诊量和趋势。
- 标出转诊量明显下降的医生，生成拜访名单。
- 每周由 Claude 根据统计结果写一段文字摘要；数字全部来自查询结果，不让模型自己算。

* [ ] 筛选和趋势图可用
* [ ] 周报里的每个数字都能在看板上对上

### 系统 17 · 转诊医生门户 Referring Physician Portal

- 转诊医生独立登录，在线开单（结构化表单加自由文本），提交后进入阶段 2 的流水线。
- 只能查看自己病人的预约状态和已签发报告。
- 所有访问写入审计记录。

* [ ] 开单后，员工端能看到分级和方案建议
* [ ] 访问别人的病人返回 403 并被审计

### 系统 18 · 账单核对 Billing & Claims QA

- 把已完成的检查和已提交的账单逐条对账，找出漏提交、重复提交、计费代码与实际检查不符、被拒的账单。
- 计费代码用合成代码表，不使用真实 OHIP 收费表。
- 差异进入工作队列，可标记处理结果。

* [ ] 能找出 seed 数据里故意埋下的每类差异
* [ ] 差异列表可导出

### 系统 19 · 患者反馈 Patient Feedback

- 检查完成后按首选语言发满意度问卷（评分加自由文本）。
- Claude 给自由文本分情绪和主题（等待时间、员工态度、环境、账单等）；差评立即通知站点经理。
- 按站点看评分和主题趋势。

* [ ] 差评触发通知
* [ ] 主题分类有小评测集

### 系统 20 · PHIPA 访问监控 PHIPA Access Monitoring

- 在审计日志上跑规则：访问不在本站点就诊的病人、非工作时间访问、短时间大量访问、访问同姓病人（可能是家属）、员工查看自己的病历。
- 每条告警附风险分和证据，进入调查队列，处理结果留档；可生成合规报表。
- Seed 数据里预埋几种异常访问，用于演示。

* [ ] 预埋的每种异常都能被抓到
* [ ] 调查处理全程留痕

### 系统 21 · 迎检中心 Inspection Readiness Hub

- 集中存放质控记录（来自系统 13 和 14）、带版本的制度文件、设备档案（保养、质控测试、维修）、员工资质（执照、证书及到期日）。
- 资质和设备检测到期前自动提醒；迎检清单显示每一项是否齐全。
- 用 Claude 做制度问答：只根据已上传的文件回答，每个回答附原文引用，找不到就明说找不到。

* [ ] 到期提醒按时出现
* [ ] 每个问答结果都带可点击的出处

## Claude 调用规范与 AI 评测

所有 AI 功能共用一个 Claude 调用层，每个功能各带一个能一条命令重跑的评测集。

调用规范：

- 去标识化：发给 Claude 前，替换姓名、健康卡号、电话、地址，出生日期换成年龄；影像去掉 DICOM 患者字段。
- 结构化输出：每个任务定义 Pydantic schema，用工具调用或 JSON schema 约束输出；校验失败自动重试一次，再失败就转为“需人工处理”。
- Prompt 管理：模板放在 `app/llm/prompts/`，带版本号，每次调用记录所用版本。
- 模型选择：模型 ID 放环境变量；推理和视觉任务用 Sonnet 档，简单分类和抽取用 Haiku 档。
- 调用日志：记录任务名、模型、prompt 版本、token、耗时、成本、成败和输入哈希，不存 PHI 原文。
- 降级：超时、限流或 API 故障时，业务流程照常进行，AI 字段显示“暂不可用”。
- 人在回路：界面上能区分哪些内容由 AI 生成；确认人和确认时间入库。

评测集放在 `evals/`，`make eval` 一条命令跑完，结果写入 `evals/results/`，应用里有对应的评测页。

| 功能 | 评测集 | 指标 |
| --- | --- | --- |
| 申请单抽取 | 50 张合成申请单，人工标注字段 | 字段级准确率 |
| 分诊排序 | 同一批 50 张，标注优先级 | 分档一致率、高估与低估比例 |
| 扫描方案推荐 | 40 条临床指征及正确方案 | Top-1、Top-3 命中率 |
| 胸片报告 | 从公开数据集抽 100 张 | 各发现类别与标签的一致率 |
| MRI 植入物抽取 | 30 段患者自述 | 器械识别准确率 |
| 患者反馈分类 | 60 条反馈 | 主题与情绪准确率 |
| 语音前台 | 20 个脚本化通话场景 | 任务完成率、平均响应延迟 |

公开数据集的标签本身有噪声，胸片评测只看趋势，不当作临床准确率。

## 给 Claude Code 的工作约定与部署

按阶段顺序做；每个系统都要能演示、有测试、有进度记录，才开始下一个。使用方式：把本文档导出为 Markdown，放进仓库的 `docs/SPEC.md`，并在 `CLAUDE.md` 里注明开工前先读它。

工作流程：

1. 开工前通读本文档，在 `docs/PROGRESS.md` 列出当前阶段的任务清单。
2. 按阶段 0 到 4 的顺序实现；上一阶段没通过验收，不开始下一阶段。
3. 每个系统的后端放 `app/modules/<system>/`，前端放 `src/features/<system>/`。
4. 每个系统下的勾选项就是它的验收标准。做完后跑通单元测试和至少一个 Playwright 端到端测试，更新 `PROGRESS.md`，单独提交。
5. 要改核心数据模型或技术栈时，先写明理由，确认后再动。

规则：

- 不使用任何真实患者数据；API key 只放 `.env`，不进仓库。
- 界面按真实产品标准做：统一的设计系统，有加载、空状态和错误提示，不做成报表页。
- 患者端页面适配手机。

演示与部署：

- 演示模式：登录页一键选角色；首页提供“重置演示数据”按钮和演示主线的分步引导。
- 公开部署：部署到个人子域名，加访问口令和 Claude 调用限额，防止 API 费用被刷。
